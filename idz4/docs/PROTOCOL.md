# Архитектура и протокол

## Распределение ролей

- Сервер хранит посылки, FIFO-очереди, занятые устройства и результаты. Он выдаёт задания и принимает завершения через TCP
- source моделирует поступление посылок; scanner - чтение маркировки; sorter - сортировку; belt - перевозку по направлению; unload - разгрузку выхода или ручного накопителя
- Посылка - самостоятельная запись с постоянным ID, стадией и состоянием маркировки. В ИДЗ4 она не требует отдельного процесса: сетевыми участниками выбраны устройства и источники
- observer получает атомарный снимок всей модели и все последующие события, включая подключения и отключения

Сервер выполняет один цикл `poll`, рабочий клиент - один цикл `poll` и таймер текущего задания.
Потоков pthread нет. Каждая роль запускается отдельным процессом, в том числе на другом компьютере.
Рабочих процессов L+S+R+2D+1, где L - источники, S - сканеры, R - сортировщики,
D - направления. Плюс сервер и произвольное число наблюдателей в пределах лимита соединений.
По умолчанию 13 рабочих процессов. Сервер не запускает их сам.

## Формат TCP

Версия 1, ASCII, строки с окончанием LF, не более 511 байт до LF.
TCP не сохраняет границы сообщений: неполные строки накапливаются, несколько строк
в одном `recv` разбираются отдельно. `send` может отправить только часть буфера:
остаток сохраняется до следующего POLLOUT. CR, NUL и непечатные байты запрещены.

| Направление | Сообщение | Назначение |
|---|---|---|
| клиент → сервер | `HELLO 1 worker scanner 1` | занять роль и номер |
| клиент → сервер | `HELLO 1 observer` | подключить наблюдателя |
| сервер → клиент | `WELCOME worker scanner 1` / `WELCOME observer` | регистрация принята |
| сервер → рабочий | `JOB token parcel duration_ms result` | выполнить действие с задержкой |
| рабочий → сервер | `DONE token result` | сообщить о завершении |
| сервер → рабочий | `ACK token` | ответ обработан; устаревший ответ не меняет модель |
| сервер → клиент | `PING` | проверка связи раз в секунду |
| клиент → сервер | `PONG` | подтверждение связи |
| клиент → сервер | `BYE` | добровольное отключение |
| сервер → все | `SUMMARY ...`, `STOP reason` | итоги и завершение |

Для сканера result=1 означает успешное чтение, 0 - ошибку. Для остальных ролей result=0.
Сервер выбирает результаты и интервалы по отдельному генератору каждой посылки,
чтобы seed воспроизводил её маршрут независимо от сетевого расписания. Рабочие
процессы моделируют длительность операции и возвращают результат задания.
Переподключение не генерирует новый случайный результат для уже выданного задания.

Неизвестная версия, неверный формат, занятая роль, неизвестный номер или результат,
не совпадающий с заданием, приводят к закрытию этого соединения. Модель сохраняется.
Это учебный протокол для доверенной сети, без TLS и аутентификации ролей.

## Снимок и наблюдение

После WELCOME наблюдатель получает `BEGIN seq=...`, строки `QUEUE`, `PARCEL`, `WORKER`,
`SUMMARY reason=snapshot` и `END seq=...`. Значения seq в BEGIN и END одинаковы:
во время построения снимка модель не меняется. PARCEL содержит расположение и позицию
в очереди; WORKER - подключение, посылку и токен. Затем поступают события `E seq=...`.

События: CONNECT/DISCONNECT - соединения; RUN - начало работы; TAKE - взятие из очереди
или создание у источника; START/FINISH - операция; RETRY - повтор чтения;
WAIT - заполненный следующий накопитель; PUT - передача в очередь; FINAL - завершение посылки.
Каждое событие содержит время, ID посылки, стадию, роль и номер устройства,
очередь и её длину, направление, число попыток и результат.

Стадии: 0 NEW, 1 SOURCE, 2 INPUT, 3 SCAN, 4 SORT_QUEUE, 5 SORT,
6 BELT_QUEUE, 7 BELT, 8 OUTPUT, 9 MANUAL, 10 DONE, 11 REJECTED.
Очереди: 0 - вход, 1 - сортировка, 2..D+1 - конвейеры,
D+2..2D+1 - выходы, 2D+2 - ручной накопитель. Направления в протоколе начинаются с 1.

На соединение выделено 128 КиБ исходящего буфера. При переполнении отключается
только медленный клиент. При возврате наблюдатель получает новый снимок, поэтому
история пропущенных событий ему не нужна для восстановления текущей картины.
Лимит - 256 одновременных соединений; неподтвердившие регистрацию и heartbeat
соединения закрываются через 5 секунд. За проход принимается не более 32 соединений,
читается не более 4096 байт с каждого, чтобы один клиент не занимал весь цикл.

## Корректность и восстановление

Сервер - единственный писатель состояния. Токен задания меняется при каждой новой
операции; DONE принимается только от соединения, владеющего ролью, для её текущего
токена и только один раз. Повторный/устаревший DONE получает ACK, но не двигает посылку.
После отключения роль остаётся занята заданием, а не сокетом. После нового HELLO
сервер либо повторяет JOB с тем же токеном, либо ждёт освобождения следующей очереди,
если DONE уже был принят. Вычисление может повториться, переход состояния - нет.

Обработанное устройство удерживает посылку при заполненной следующей очереди.
Повторное сканирование выполняется на том же сканере: возврат в заполненную входную
очередь мог бы создать взаимную блокировку. Очереди FIFO, добавление/извлечение O(1).
Полная проверка: O(N+J+Q), цикл планирования: O(J), рассылка события: O(C).
Построение снимка: O(N*(N+J+Q)), при N<=512 это допустимо; можно улучшить обратными индексами.
Буферы соединений резервируют около 32 МиБ, это сознательный обмен памяти на простоту.

При корректном завершении сервер сначала передаёт SUMMARY/STOP, затем делает
`shutdown(SHUT_WR)` и дочитывает вход до закрытия клиента, максимум 2 секунды.
Это уменьшает риск TCP RST из-за непрочитанных ответов. Все сокеты закрываются;
именованных IPC-объектов в этой версии нет.

Состояние живёт в памяти сервера. Его аварийный перезапуск начинает новую модель.
Без сети доставить STOP невозможно; в этом случае клиент использует обнаружение
разрыва/heartbeat и ограниченные повторы подключения. Порядок событий при одинаковом
seed может отличаться. Сохранённый маршрут относится к посылке, а не к расписанию.
